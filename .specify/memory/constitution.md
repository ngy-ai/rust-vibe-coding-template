# Rust Vibe Coding Template Constitution

## Core Principles

### I. 源码文件规模与拆分 (NON-NEGOTIABLE)

源码文件不能过大：大文件既难阅读也难修改，工具读一次就吃掉上下文。

- **单个源码文件不得超过约 700 行**。
- 超过上限就必须按职责拆成子模块，不要继续往上堆。
- 新增代码时如果目标文件已经接近这个上限，先拆再改，不允许"先写完再说"。
- 拆分是独立的改动：拆完后单独 `git commit`，不与功能改动混在同一次提交里。
- 行数按文件实际内容计（含注释与文档注释），不靠压缩格式、删除注释或合并语句来达标。

**Rationale**: 约 700 行是一次可以完整读完、可以安全重构的上限；超过之后人工评审质量与 AI
工具的上下文效率同时下降。把"先拆再改"写成前置条件，才能防止上限被渐进式突破。

### II. 代码质量与可维护性 (NON-NEGOTIABLE)

代码必须靠命名与结构自解释；注释只解释为什么，不复述做了什么。

- **合并门禁**：每次变更必须通过 `cargo fmt --check` 与
  `cargo clippy --all-targets --all-features -- -D warnings`，且不得靠新增 lint
  抑制属性来换取通过。
- **契约文档**：公共接口（`pub fn`、`pub trait`、模块对外 API）必须用文档注释
  写明契约——输入、输出、错误模式，以及会 panic 的条件。
- **死代码**：不得合并。以下情形按定义不属于死代码，无需申报：trait 实现、
  `#[cfg(...)]` 平台/feature 分支、`#[cfg(test)]` 辅助代码，以及标注了来源与
  再生成命令的生成代码。其余确需保留的未使用项，只允许
  `#[expect(dead_code, reason = "<理由>，见 #<issue>")]`；
  `#[allow(dead_code)]` 与没有 issue 归属的理由一律不接受。
- **被注释掉的代码**：不得合并，不再使用的实现直接删除，留档由 git 历史承担。
  解释为何不采用某方案的文字注释不受此限；rustdoc 中标注 `no_run` 或 `ignore`
  的示例代码不受此限。
- **TODO / FIXME**：只允许 issue 归属形式，固定格式为
  `TODO(#<issue>): <说明>`，说明中必须给出触发条件或清理期限。裸 `TODO:`、
  `TODO(TBD)`、`TODO(later)` 一类无归属写法不得合并；对应 issue 关闭时，必须在
  同一提交内删除该 TODO。
- **复杂度**：单个函数圈复杂度保持低位；函数超出合理规模时必须在合并前分解，
  不得以以后再重构为由延期。

**Rationale**: 代码被阅读的次数远多于被编写的次数，而存在却不生效的东西
（死代码、注释掉的实现、无主 TODO）利息最高——它们不进测试覆盖、不参与编译与
lint 检查、也没有人负责，却持续向读者传递错误预期。把标准前移到合并时执行，
才能防止债务缓慢累积到代码库无法维护。豁免只给工具看不见用途的客观情形，不给
以后再说的裁量权；`#[expect]` 在 lint 不再触发时会自动报警，使豁免自带过期机制。

### III. 测试先行开发 (NON-NEGOTIABLE)

从第一个真实 feature 起，功能工作与缺陷修复一律测试先行：

1. 先写测试，再写实现。
2. 实现之前必须先运行测试并观察到它失败；没有观察到失败的测试不算数。
3. 实现只写让测试通过所需的最少代码，转绿之后再重构。
4. 每个对外接口必须有契约测试：CLI 命令覆盖参数、标准输出与退出码；公共库 API
   覆盖输入、返回值与错误类型。
5. 单元测试覆盖内部逻辑的非平凡分支与错误路径，不只覆盖正常路径。
6. 新增生产代码却没有对应的先失败后通过测试的 PR 不予合入。
7. 最少实现不等于可以省掉错误处理：错误模式与文档注释仍须满足原则 II。

**不适用**：纯重构与拆分（行为不变，由既有测试守护）、文档与配置、CI 与脚手架本身。

**Rationale**: 这条对 AI 参与的开发比对人工开发更关键——模型天然倾向于生成看起来对的
代码，而先失败的测试是唯一能证明实现真的在工作的证据。测试先行同时迫使契约在实现之前
被想清楚，防止过度工程化，并留下随代码库寿命增值的回归网。

### IV. 对外接触面一致性

对外接触面（CLI、公共库 API、错误消息）必须全项目一致：

- 命名、参数风格、错误结构与退出码遵循单一文档化约定，不因模块而异。
- 错误信息必须可执行：说清哪个输入有问题、期望是什么、如何修正。错误是人类与 AI
  共用的调试输入，含糊的错误会直接让下一轮修复跑偏。
- 接触面的破坏性变更按治理中的版本规则处理，并附迁移说明；不得静默改变既有行为。
- 新增接触面之前先确认是否应并入已有命令或已有类型；只为表面清晰而新增
  CLI 子命令或包装类型，与原则 I 反对的碎片化同样不合规。

**Rationale**: 一致性降低使用者的认知负担，而且对 AI 尤其重要——统一的错误结构与命名
让模型不必为每个模块重新推断调用约定。这是成本最低、收益最持久的一类可用性投入。

### V. 性能与效率

性能是功能的一部分，不是事后的优化项。本模板给出一组默认预算，派生项目可以收紧，也可以
在 feature 的 plan 复杂度追踪中记录显式例外——但不得把预算改成无法测量的形式。

**默认预算**（派生项目应在第一次 plan 时确认，未确认即视为沿用）：

- CLI 命令：预热后单次执行 p95 < 100ms，不含外部进程与网络等待。
- 公共库 API：单次调用 p95 < 1ms；含 IO 的接口单独声明预算，不与纯计算接口混用。
- 内存：CLI 常驻峰值 < 100MB；流式处理时中间副本总量不得超过输入规模的一个常量倍数。

**测量方式**（参数须写进对应 feature 的 plan，而不是只写在 PR 描述里）：

- 端到端（CLI、批处理）：用 `hyperfine`，至少 5 次预热、20 次采样，固定同一台机器与
  同一组输入；用 `--export-json` 的结果计算 p95 与中位数，不用平均值代替。
- 微基准（函数、数据结构）：用 `criterion`，`cargo bench` 默认统计即可；比较时报告
  两次测量的置信区间是否重叠，重叠即视为无差异。
- 内存：Linux 用 `/usr/bin/time -v`，Windows 用 `Get-Process` 采样 `WorkingSet`；
  不得用代码里的计时或计数替代外部观测。
- 基准必须能用一条命令复现，命令写进 plan。工具只在真正要测量时才加入
  `[dev-dependencies]`，且与第一个基准一并提交——避免依赖先进、用处后到。

**禁止形态**（无需声明预算即生效）：

- 热路径上的二次复杂度：对同一集合嵌套遍历，或对可索引内容做线性查找。
- 循环内的重复分配与克隆：能借用就不 `clone()`，能复用缓冲就不新建 `Vec` / `String`。
- 无上界缓冲：一次读入整个输入，或把不确定长度的序列收进内存——除非在代码中写明
  约束来源（输入上限、协议限制）。
- 为以后可能用到而预先建索引或缓存：与死代码同理，没有当前消费者就不建。

引入缓存必须同时写明失效条件与容量上限，写在缓存实现旁边，不写在别处。

**证据要求**：涉及性能的变更必须在 PR 中附测量结果，并与变更前对比；测量按上面约定的
方式执行。没有测量的性能优化不予合入——它与原则 II 里无法说明理由的抽象同理。

**Rationale**: 模型生成的代码倾向于在正确性上过关、在复杂度上失控：O(n²) 在十条数据上
看不出来，等真实规模进来才暴露，那时修复成本已经高一个量级。给模板预置可测量的默认预算
与一组具体禁止形态，比任何抽象的性能目标都更容易被 AI 与评审者执行；而预算是唯一必须
可测的条款，所以它必须留下明确的量化和收紧路径。

### VI. 简单性与 YAGNI

默认是单 crate、单可部署单元。任何功能的初始实现最多涉及三个单元（例如一个 bin 加一个
lib 加一个共享 crate）；要加第四个，必须先在 plan 的复杂度追踪里给出理由。

- 不预留未来功能：没有当前消费者的配置项、环境变量、feature flag 与公开 API 一律不写。
  第二个具体调用者出现时再加，而不是提前。
- 不写推测性抽象：trait、泛型参数、newtype 包装各自都要有当下的理由。仅为以后可能换
  实现而引入 trait 不算理由；为在测试中替换实现、或已有两处真实差异而引入才算。
- 直接使用依赖与标准库已有的能力。只有包装层编码了原语本身不具备的不变量（单位换算、
  输入校验、状态约束）时，才允许在项目内再包一层。
- 三行相似代码优于过早抽象：重复第二次可以忍，第三次出现且形态稳定时再提取。
- 抽象的成本包含类型复杂度本身：泛型参数个数、trait bound、生命周期标注与动态分发都算，
  不只是行数或文件数。

**Rationale**: 每个抽象都是对未来读者的税，而模型尤其倾向于生成看起来更有架构的东西——
Repository 层、Service 层、随处可见的 Builder。在 Rust 里这些会以泛型展开、trait object
与编译时间的形式直接计费。推迟到它真的付租金时再做，代码库才能保持诚实。

### VII. 可观测性与结构化日志

日志是模板的通用能力，不是可选项。凡产生运行时行为的入口（CLI 命令、库的主入口、
长期运行进程）都必须发出可机器解析的结构化日志。

- 格式：结构化键值（JSON 或等效形式），字段名全项目统一；不以拼接出来的自由文本作为
  主要记录形式。
- 每条记录至少包含操作名、结果（成功，或错误类别）与耗时；存在跨进程或跨服务调用时，
  还必须带上可传播的相关 ID。
- 错误在被处理的边界处记录，且只记录一次：不逐层重复打点，也不在向上返回错误的同时
  再记录一遍。上下文要足以在无需复现的情况下定位问题。
- 日志通道与级别由应用模式决定：
  - development：控制台详尽输出，写 stdout；本项目 crate 默认 debug，依赖保持 info。
  - test：stdout 与 JSON 文件双写，控制台供即时观察，文件供事后核对。
  - production：只写 JSON 文件，stdout 保持洁净；默认 info，仅保留启动/退出、错误
    与关键状态变更，逐步骤调试信息必须关闭。
- 敏感信息：不得记录凭据、令牌、PII 或完整请求/响应体；不要把整个结构体用 `{:?}`
  丢进日志，只记录明确列出的字段。
- 级别名称遵循统一约定（error / warn / info / debug / trace），其上可被 `RUST_LOG`
  一类环境变量覆盖。
- 日志不得破坏原则 V 的预算：热路径上禁止无条件的字符串拼接与 `{:?}` 格式化，需要时
  先做级别检查，或使用惰性字段。

**Rationale**: 事故的胜负取决于凌晨三点能拿到的遥测质量，结构化且一致的日志是其他一切
排查的前提。在这个模板里它还有一层含义——日志既给人看，也给 AI 读：统一字段名与
随模式固定的输出通道，让后续自动化分析无需额外适配即可使用。

### VIII. 安全基线

安全要求适用于每个功能，并在评审时执行：

- **输入验证在边界**：所有跨信任边界的输入（CLI 参数、环境变量、配置文件、文件内容、
  网络或消息负载）必须在入口处验证并转换成受限类型，再传给业务逻辑；不在业务逻辑深处
  做兜底校验。拒绝时要按原则 IV 说明哪一项输入不合法、期望什么。
- **注入**：禁止把外部字符串拼接进会被解释器执行的位置——shell 命令、SQL、路径、模板。
  子进程一律走参数化接口，SQL 走参数绑定，路径必须校验不会逃出允许的根目录。
- **不可信输出**：把不可信内容写到终端或日志前，需处理 ANSI 控制序列与换行注入，
  避免伪造日志行或清屏。
- **机密**：凭据、令牌、私钥不得入库；本地用 `.env`（已被忽略），部署用环境注入或
  机密管理器。CI 必须拦截私钥块、常见令牌格式与被误提交的 `.env`。
- **依赖**：引入新依赖前确认维护状态与已知漏洞；`cargo audit` 必须在 CI 通过。
  出现漏洞按严重程度限期升级，高危不得带病合并。
- **认证与授权**：只有涉及认证、授权、会话或访问控制的功能才触发专门安全审查；
  没有这类功能时不预写相关实现（见原则 VI）。

**Rationale**: 这个模板会被复制到真实项目里，安全缺陷会连同骨架一起被复制。把要求放在
输入边界、注入点与机密切口三处，是因为这三处是唯一无法靠编译器兜住的地方——Rust 能把住
内存与线程，但管不住「把用户输入拼进命令」和「把令牌写进仓库」。

## Rust 代码组织约定

### 模块拆分布局

- 拆分沿用 Rust 2018+ 的模块布局：`foo.rs` 拆成 `foo.rs`（模块根）加若干 `foo/*.rs`。
- 不新增 `mod.rs`：`foo.rs` 与 `foo/` 目录并存即可，子模块由 `foo.rs` 中的 `mod` 声明挂载。
- 模块根（`lib.rs`、`main.rs`、`foo.rs`）只放文档、`mod` 声明和对外导出（`pub use`、
  `pub use foo::xxx;` 这类重导出）；共享类型必须单独成文件、文件名按职责命名
  （如 `model.rs`、`config.rs`），不在模块根就地定义。
- 实现按职责分文件：文件名应当描述职责（如 `parser.rs`、`http.rs`），不按类型机械切分。
  同一类型的实现可以分散在多个文件里，不受"一个类型一个文件"限制。

### 测试布局

- 测试同样拆分，并镜像源码布局：
  - 单元测试留在被测模块内，用 `#[cfg(test)] mod tests` 就近覆盖私有实现。
  - 集成测试放 `tests/<module>_test.rs`，与源码目录 `src/<module>/` 一一对应。
  - 跨模块的集成测试留在 `tests/`。
- 测试文件名必须带 `_test` 后缀，例如 `parser.rs` 的测试叫 `parser_test.rs`。
- `tests/` 下的每个文件都是独立 crate，公共测试辅助代码放在 `tests/common/` 或用
  `mod common;` 显式引入，不要在测试文件之间互相 `use`。

## 开发流程与质量门禁

- 纯拆分提交只做文件移动、`mod` 声明与再导出调整，不改变行为；行为改动放在后续提交里。
- 拆分提交必须保证 `cargo build` 与 `cargo test` 通过，且不改变公开 API 语义。
- 代码评审必须检查：改动后的文件是否 ≤ 700 行、文件是否按职责拆分、模块是否只依赖
  共享基础设施、测试是否镜像源码布局。
- 新增文件前先确认它属于哪个模块、是否应该并入已有文件；只为"看起来更小"而制造碎片化
  同样不合规。
- 违规的大文件不得以"稍后重构"为由合入。

## Governance

- 本 Constitution 优先于其他开发惯例；与其他实践冲突时，以本文件为准。
- 修订必须说明理由、影响范围和迁移方案，并按语义化版本递增：
  - MAJOR：删除或重定义原则，产生不兼容的治理变更。
  - MINOR：新增原则或章节，或对现有指导作实质性扩展。
  - PATCH：措辞澄清、笔误修正等非语义性调整。
- 所有 PR / 评审必须验证合规性，其中文件规模上限、模块边界、测试布局、代码质量门禁
  （fmt / clippy / 契约文档 / 死代码与 TODO 归属）、测试先行与契约测试、接触面一致性、
  性能预算与测量证据、简单性（单元数量、无预留配置与推测性抽象）、可观测性
  （结构化字段、按模式的输出通道、敏感信息）、安全基线（输入边界、注入、机密、依赖）
  为强制检查项。
- 复杂度必须可被证明是必要的；无法说明理由的额外抽象或跨模块依赖不予合入。

### 单开发者仓库条款

本仓库当前只有一个活跃维护者（以 `CODEOWNERS` 或等效记录为准）。涉及安全的变更，
上述「专门安全审查 + 第二审批人」要求由同一人履行两个角色，且以下条件不可放弃：

1. 专门的安全审查必须完整执行，结论、证据链接与未决发现记录在 PR 描述中。
2. PR 描述必须包含自我证明：维护者、日期、审查结论、逐项重查的条款清单，以及明确
   承认自己同时担任实施者与审批人（仓库无其他活跃维护者）。
3. 该记录必须标注「单开发者仓库条款」，便于第二个维护者加入后识别历史签署。
4. 一旦出现第二个活跃维护者，独立审查与第二审批人要求立即对**新** PR 恢复；
   历史自我证明不追溯作废。

本条款只移除「第二审批人必须是另一个人类」这一结构性要求，不豁免专门审查本身、
安全控制的实施、机密扫描或依赖禁令。
